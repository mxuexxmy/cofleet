# Docker 应用观察与统一访问方案

状态：M1/M2 代码已在 CoFleet 0.7.0 实现，自动化协议与持久化测试通过；M1 Linux 原生 Docker 只读与浏览器回归已验证，见 [M1 验收记录](m1-observe.md)；M2 真实已有项目、独立访问域和多账号验收尚未完成。当前 LPK 默认不配置访问域，因此可使用只读发现与日志，但正式入口创建保持关闭。记录日期：2026-11-04（Asia/Shanghai）。

### 0.7.0 实现说明

- Agent 使用独立 `--docker-observe` 开关启用只读发现、日志和入口授权，不依赖固定测试容器的 `--docker` 开关；
- Manager 使用 SQLite `state.sqlite3` 保存入口意图、owner、绑定、启用状态和 revision，数据库损坏或 schema 不兼容时拒绝启动；
- 观察结果按 6 KiB 控制帧分片，单次总量限制 128 KiB；目录每页最多 50 个容器，日志最多 500 行／16 KiB；
- 精确容器绑定只接受完整容器 ID；Compose 绑定仅在唯一、运行中、非 one-off 候选存在时重连；
- 隧道消息只携带入口 ID 和 revision。Agent 从本机私有授权账本取定义，每次连接重新核验容器和回环发布端口；活跃流每 5 秒复核，映射或授权变化后关闭；
- 禁用和删除入口先提交 Manager 意图、阻止新访问并广播断流，再尝试撤销在线 Agent 授权；Agent 离线不阻塞删除；
- 应用代理保留第三方应用 Cookie 与 Authorization，剥离平台／CoFleet Cookie、身份头和伪造转发头，移除上游 Cookie 的 Domain 属性，支持相对/批准来源重定向、WebSocket、32 MiB 请求体上限和 HTTPS 证书校验；
- 管理 UI 已增加“应用入口”页，可发现服务、读取有界日志、按 Compose 或完整容器绑定、添加、打开、禁用和删除入口。

正式访问仍有部署门槛：Manager 必须显式配置 `--access-domain <独立域>`，且该域与管理 Host 的 Cookie Site 不同；否则创建返回 HTTP 412。该访问域还必须在目标微服上实测动态 Host 路由、TLS 和平台登录。不能用管理端同源路径绕过这个门槛。LPK 启动脚本只在明确提供 `COFLEET_ACCESS_DOMAIN` 时传入该参数，仓库默认清单不设置它。

## 1. 结论与产品定位

方案可行。CoFleet 负责发现已有 Docker 服务、查看运行情况和提供经过登录保护的访问入口；部署、配置、升级、数据维护继续在原工具中完成。参考 1Panel 的容器信息呈现与应用入口组织方式，不引入其整套部署管理流程。

核心用户故事：用户已经通过 1Panel、Compose、命令行或其他工具运行一个 Web 应用，在 CoFleet 找到它、查看最近日志、添加访问入口，随后从任意已登录终端打开；应用重建和维护仍回到原工具进行。

### 功能边界

| 第一版提供 | 原工具继续负责／本轮不提供 |
| --- | --- |
| 按电脑、Compose 项目浏览容器，查看状态、镜像与已发布端口 | 安装、创建、启动、停止、重启、删除或重建外部容器 |
| 查看容器健康信息及最近日志 | 修改 Compose、环境变量、网络、卷、重启策略 |
| 手动添加、禁用、删除 CoFleet 访问入口 | 拉取镜像、升级、备份、迁移、自动调度 |
| HTTP 应用和 WebSocket 的统一访问 | 通用 TCP/UDP 转发、SSH、终端、exec、数据库客户端接入 |
| 手动填写原管理工具链接 | 猜测管理工具归属、读取磁盘上的 Compose 配置或项目文件 |

删除入口只删除 CoFleet 的访问配置并关闭相应隧道，原容器和数据不变。管理中心、Agent 离线或卸载均不停止这些外部应用。保留现有 CoFleet 开发空间、构建发布和固定测试容器能力，沿用其原有独立授权；新观察模块不能调用这些变更接口操作外部容器。

因此，“可以复用现有传输机制”不等于“已有通用应用网关”。验收必须分别覆盖发现、授权、代理兼容和状态恢复。

## 3. 信息组织与操作流程

一级导航新增“应用入口”；设备详情中的“容器”展示只读 Docker 资源。应用入口集中展示用户主动添加的服务，Docker 资源展示已发现的容器，二者都能跳转到对应设备。

应用入口条目显示：名称、电脑、项目／服务、连接状态、访问状态、最近核验时间，以及“打开应用、查看日志、编辑入口、前往原管理工具”。禁用或失效时保留配置和原因，不显示成可用。

设备容器按 Compose 项目分组；没有标签时归入“独立容器”。仅凭 Docker 标准标签识别项目与服务，不能据此断言由 1Panel 创建；同名项目必须带设备及 Docker 环境上下文。

### 添加入口

1. 选择设备、容器和 Docker 已发布的 TCP 服务端口；展示容器端口与宿主映射，用户确认它是 Web 服务。
2. 填写名称；协议默认为 HTTP，可选 HTTPS。原管理地址为可选的外部 http/https 链接，打开新标签页且不转发 CoFleet 凭据。
3. 自动生成不可猜测的入口标识和独立来源地址，不要求用户配置 DNS。
4. Agent 核验容器身份与端口后，仅做一次有限 HTTP 连通性探测；不调用应用变更操作。401/403 代表需要应用登录，不应标记为应用故障；失败不自动尝试其他端口。
5. 保存入口，显示“已核验可连接／待核验／不可连接”。运行状态、Docker 健康状态、入口连通性分别显示，无 Docker healthcheck 时显示“未配置健康检查”。

第一版不提供容器资源使用的高频采样、历史图表或实时日志追踪。最近日志默认 100 行，最多 500 行、16 KiB，单次请求最长 10 秒；返回截断标记。只支持 Docker 能返回的 stdout/stderr，不读取容器内文件；日志驱动不支持读取时解释原因。日志不写入管理中心数据库，也不放进每次心跳；用户主动刷新，错误与空日志分别显示。

## 4. 容器身份与访问目标

### 发现方式

增加独立、本机显式启用的 Docker 观察能力，例如 `--docker-observe`，不要求开启现有测试容器执行器。第一版使用 Agent 本机 Docker CLI 和固定参数数组，复用现有调用基础；不拼接 shell，不提供透传 CLI 或 Docker API。后续如切换 Engine API，保持相同授权边界。

初次启用针对一个明确的本机 Docker 环境；不支持任意远端 DOCKER_HOST、运行时切换 context 或同一 Agent 同时浏览多个引擎。环境变化后暂停所有入口，要求本机重新确认。Windows Docker Desktop／WSL 分别视为明确执行环境，不把它们与 Linux 宿主混为同一环境。

新列表按 50 条分页，单页最多 128 KiB，使用短时发现快照的游标；快照过期要求重新查询。容器增删或发现失败不能清空用户保存的入口。仅缓存当前快照，5 秒内复用，设备在线不表示 Docker 可用。日志必须使用已发现且重新 inspect 核对的完整容器 ID。

### 绑定规则

| 类型 | 保存的逻辑绑定 | 重建后的行为 |
| --- | --- | --- |
| Compose 服务 | 设备、Docker 环境标识、project、service、容器端口、TCP 协议 | 原容器仍存在时继续精确绑定；原容器已消失且仅有一个符合标签与端口的运行中非 one-off 候选时允许重新关联，并记录变更 |
| 独立容器 | 设备、Docker 环境标识、完整容器 ID、容器端口、TCP 协议 | 删除或重建后要求用户重新选择；同名容器不自动继承 |

Compose 标签用于同一已授权 Docker 环境内的服务识别，不是身份认证。默认选择服务绑定时，界面明确告知“同项目同服务重建后继续关联”；用户可改成精确容器绑定。存在多个副本、one-off 容器、多组可用映射或运行中旧新副本重叠时，不做负载均衡或猜测，提示明确选择。

每次新建隧道都重新核对容器 ID、运行状态、逻辑绑定和当前端口映射；不能仅根据保存的宿主端口拨号。暂停、禁用、删除、绑定变化或环境变化时，关闭该入口已有隧道，下一次访问重新核对。外部工具变更会有发现延迟；第一版以 5 秒周期复核活跃入口，不能宣称原子锁定其他工具的 Docker 变更。

### 网络支持范围

第一版只连接本机引擎明确发布、在 Agent 所处网络环境中可由回环访问的 TCP 端口：IPv4 `127.0.0.1`／`0.0.0.0` 映射到 `127.0.0.1`，IPv6 `::1`／`::` 映射到 `::1`；不将 wildcard 地址作为拨号目标。仅绑定特定网卡 IP 的映射先显示“不支持此绑定”，由用户在原工具调整。

不进入容器网络、不直接连接容器 IP，不更改现有端口映射。只有 EXPOSE、没有发布端口，以及 host network、macvlan、UDP 服务，第一版均不创建入口。不能从端口号推断应用协议。Docker Desktop／WSL 的回环可达性必须在相应环境实测，未通过时不能标记支持。

## 5. 访问架构与浏览器边界

```text
浏览器访问每个入口的独立 HTTPS 来源
  → 平台登录及可信入口
  → CoFleet：域名映射、账号与设备归属、入口启用状态
  → 已授权设备的独立反向 WSS 数据流
  → Agent：入口版本、容器身份、当前端口映射核对
  → 本机已发布的 Web 服务
```

流量经过微服，微服承担带宽与连接开销；不承诺直连、连接无缝迁移或流媒体吞吐。沿用现有总连接数与每节点连接数限制，大请求使用有背压的流式传输；首版沿用当前 32 MiB 请求体上限，连接建立超时 15 秒。长连接受并发和空闲超时约束，超限给出明确错误，不无限缓存。

### 独立来源为正式访问的前置条件

2026-11-04 M0 实测补充：独立来源不足以阻止应用 JavaScript 写入共同父域 Cookie，原“不能设置管理域 Cookie”的严格保证尚未满足。详情及待补验收见 [M0 实测](m0-access.md)；正式访问 M2 必须先解决 M0.1 的浏览器凭据隔离，不因普通 Set-Cookie 测试通过而放行。

每个入口使用独立域名，不与管理 API 或其他外部应用共用浏览器来源；不把任意应用挂在管理端 `/apps/<id>/` 下作为通用回退。域名按管理端实际分配域名派生，例如 `e-<opaque-id>-<实际应用域名前段>`；这是待验证的命名方案，不是已可用配置。用户不能任意指定 Host。

懒猫官方说明存在前缀域名机制，但当前 exec 路由是否向后端可靠保留域名、平台登录 Cookie 如何在前缀域名工作，仍需实测。若需独立网关服务，先验证可行方案及其资源开销，再修改平台配置。无法可靠隔离域名和账号时，停在只读发现与日志阶段，不以管理端同源路径替代。

受信平台入口提供的身份与有效 Host 必须分别验证；每次 HTTP 和 WebSocket 握手均检查入口归属、设备归属及当前 Agent 会话。未知域名、未知入口及非本人资源不返回内部元数据。管理 API、设备控制通道和入口配置接口只接受管理端 Host，外部应用域名不能访问这些接口。

### Cookie、请求头和应用登录

- 平台负责允许谁访问入口，应用自身的账号与登录流程继续保留。通过 CoFleet 登录不等于自动登录第三方应用。
- 网关必须在转发前过滤平台认证 Cookie、现有 `cofleet_workspace` Cookie、可信用户身份头及控制面凭据；保留应用自己的 Cookie，支持重复 Set-Cookie。
- 应用 Set-Cookie 不得覆盖平台／CoFleet 保留名称，删除上游 Domain 属性使其限定为当前入口 Host；保留应用需要的 Path、HttpOnly、SameSite 等语义。不得删除或改写平台入口自己生成的认证 Cookie。
- 不能让应用控制管理来源的 Cookie、CORS 或认证响应。外部页面跨来源调用管理 API 时，不返回授权的跨域响应，变更接口继续要求来源校验与现有请求标记。
- 正式入口使用懒猫身份模式，Authorization 作为第三方应用凭据按目标应用转发，不能拿它作为 CoFleet 管理身份；开发模式下不能复用管理 Bearer Token 访问第三方应用，测试使用独立临时入口会话。
- 默认向上游传递入口的公开 Host、Origin 和可信计算的转发信息，不接受客户端伪造的转发头。WebSocket 校验有效来源；允许无 Origin 的普通客户端时仍必须完成入口鉴权。
- 相对重定向保留；仅将与已批准上游来源完全匹配的绝对重定向映射到入口，外部登录提供方地址保持不变。不通用改写 HTML/JavaScript，也不自动探测私网跳转；需要应用配置公开访问地址时引导回原工具配置。
- HTTPS 上游默认校验证书，SNI／证书名称必须与用户配置的有效服务名称匹配，但拨号地址仍来自已批准的本机映射，不能利用该名称拨号到任意主机。自签名证书首版显示“不支持的上游证书”，不自动关闭验证。

Cookie 过滤名单、Host 与 Origin 传递、登录重定向、应用 Authorization、CORS、平台登录失效和跨账号访问均是第一道验证关口；仅测试一个无登录静态页面不足以通过。

## 6. 持久化、授权与协议边界

### 保存什么

管理中心增加 SQLite 入口配置库，生产位置建议 `/lzcapp/var/cofleet/state.sqlite3`，使用可配置的数据目录；schema 版本化，单写入者，事务提交后才返回保存成功，损坏或迁移失败时禁止启用相关入口，不能静默新建空库覆盖。实现采用 `rusqlite` bundled，阻塞数据库操作不在 Tokio reactor 上运行。初始化目录权限随部署实测核对。

保存对象限定为：入口 UUID、所属用户、设备与 Docker 环境、绑定方式及绑定字段、显示名称、上游协议／可选证书名称、原管理链接、启用状态、配置 revision 和时间戳。不保存 Compose 内容、环境变量、应用密码、日志正文或平台登录令牌。原管理链接禁止带 userinfo 凭据，只允许 http/https，不由服务端请求。

原容器的部署意图与数据仍在原工具。管理中心保存的唯一意图是“是否提供这个访问入口”。设备快照、解析出的当前容器／宿主端口和连接状态是可重建缓存；不得把它们当作持久授权依据。

Agent 本机持久保存是否允许 Docker 观察、固定 Docker 环境以及已接受的入口授权版本；记录按当前账号和管理中心上下文隔离。隧道只携带入口 ID 与 revision，Agent 必须匹配已授权定义，在线重新核对端口，拒绝任意 URL、IP、宿主端口或不同 revision。管理中心重启后依据配置库重发定义，Agent 确认后入口才能恢复。配置落盘与入口生效分别反馈：保存成功但 Agent 未确认时显示“等待节点核验”，不能直接显示为可访问。

保存使用 revision 乐观锁，入口创建使用客户端生成 UUID 幂等重试；同一 ID 不同内容冲突需明确报错。禁用／删除先在管理中心提交并阻断新访问、关闭已有流，再通知在线 Agent 清理；Agent 离线时不阻塞删除，重连后以当前清单核对，旧授权不得重新生效。暂停“接收新任务”不影响本模块只读访问，需独立的“禁用入口／关闭观察能力”控制。

### 最小接口草案

以下按行为冻结，编码前在接口设计中补齐具体 JSON 与错误码；不直接扩充现有快照到无界大小。

| 管理 API（仅管理来源） | 行为 |
| --- | --- |
| `GET /api/v1/devices/{device}/docker/catalog` | 游标分页只读发现，返回环境标识、快照时间、容器及端口候选 |
| `GET /api/v1/devices/{device}/docker/containers/{id}/logs` | 有界最近日志，返回时间与截断信息 |
| `GET/POST /api/v1/access-endpoints` | 列出本人入口、幂等创建 |
| `PATCH/DELETE /api/v1/access-endpoints/{id}` | 带 revision 修改或删除，仅改变访问配置 |

设备能力显式声明是否支持 catalog、日志和入口隧道；旧 Agent 保留已有行为，新入口按钮显示“请升级或启用观察能力”，不能向旧端发送未知请求。新增独立观察请求与入口授权消息，保留原 Docker 测试变更枚举的范围。协议更新必须设计版本／能力协商，不能直接新增 TunnelTarget 后假设旧 Agent 能解析。

Agent 虽然只暴露只读业务动作，但访问 Docker socket／Docker 用户组本身仍具有高权限；不得把 socket 挂载到微服或通过网络开放。不把“只读 UI”描述为已经获得操作系统级 Docker 只读隔离。采集仅返回必要字段，禁止上报完整 inspect、环境变量或全部标签。

## 7. 分阶段实施与验收

### M0：独立入口兼容性验证

当前结果：工具、协议与浏览器兼容性实验已实现；16 项协议检查和 9 项浏览器兼容性检查通过，但父域 Cookie 写入门槛不通过，真实跨账号与平台端撤销待补。已清理临时环境，未启用生产通用代理。见 [结果记录](m0-access.md)。

先用一个由原工具部署、具有自身 Cookie 登录和 WebSocket 的 Web 应用，以及一个静态服务，在单个 Linux 节点验证：

- 实际前缀域名、TLS、Host 保留、平台登录、应用 Cookie 和重定向；管理接口不能从入口 Host 使用。
- 无登录、伪造身份／Host、跨用户、跨来源请求及平台登出后的新请求／新握手被正确拒绝；已有连接沿用现有会话撤销机制，不承诺平台登出瞬间撤销已建立的所有流。
- 第三方应用收不到平台 Cookie／身份头，不能设置管理域 Cookie；应用自己的 Cookie 登录、Authorization 和 WebSocket 可用。
- 目标 TLS 证书错误、路径不兼容和不支持的应用公开地址配置均有明确失败结果。

实施前重新核验微服与 CLI 版本并完成官方规范校准；本次参考基线是已验证的 lzcos 1.6.2+fix.4／lzc-cli 2.0.9，不把文档中的最新字段直接视为目标支持。输出实测记录和最终域名／鉴权方案。此阶段只使用显式固定的测试服务，不新增面向任意服务的地址输入。M0 不通过，则后续只实现 catalog 与日志，正式统一访问暂停。

### M1：只读资源与日志

实现本机 opt-in、能力协商、分页发现、Compose 分组、端口候选和有界日志。覆盖无 Docker、权限不足、日志驱动不支持、大量容器、重复项目名、缺失标签、容器消失、离线与旧 Agent。

验收：不发出创建、启动、停止、删除、exec、网络或卷修改命令；关闭观察能力后访问停止；平台 Cookie、env 和日志正文不出现在上报快照及常规运行日志。先验证 Linux，Windows Docker Desktop／WSL 单独记录结果。

### M2：持久入口与访问闭环

实现配置库、入口 UI、Agent 授权、身份解析、独立来源代理和实际访问。选择已有真实项目，不使用 CoFleet 自有测试容器冒充外部应用验证：

1. 在原工具中部署并保持运行，CoFleet 发现、查看日志、添加入口、完成应用登录与访问。
2. 在原工具中重建 Compose 服务、更换宿主映射，确认正确重新关联；同名独立容器、多个候选、环境切换及无映射时不误关联。
3. 原端口被另一个服务占用时拒绝新隧道；活跃入口复核发现变化后关闭旧流。记录外部变更竞态限制，不承诺绝对零时间窗口。
4. 管理中心重启后入口配置保留，Agent 核验后恢复；Agent／电脑重启、断网和旧会话均不能绕过授权。
5. 禁用／删除入口、卸载 CoFleet 后，原应用与数据保持；原管理入口仍由原工具维护。
6. 覆盖数据库迁移／损坏、保存响应丢失、重复创建、并发修改、跨账号查询／日志／隧道及直接访问已禁用域名。
7. 覆盖上传上限、长日志、WebSocket、并发上限、背压与超时；记录微服 CPU、内存和吞吐，不做未经测量的容量承诺。

### M3：平台与应用适配

在 M2 稳定后验证 Windows Docker Desktop／WSL、其他日志驱动和更多需要公开地址配置的应用。实时日志、容器资源采样、通用 TCP/UDP、容器网络访问和多副本均为后续单独设计，不自动进入本轮范围。
