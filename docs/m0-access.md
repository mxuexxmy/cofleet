# M0：独立入口与应用登录兼容性实测

记录日期：2026-11-04（Asia/Shanghai）。基于 0.6.1 开展独立实验，未升级或改动现有微服管理端。

**结论：验证工具及单账号兼容性实验已完成，正式统一访问门槛未通过。** HTTPS、应用 Cookie 登录、WebSocket 和只读代理链路可行，但同一微服根域下的前缀域名不能阻止应用 JavaScript 写入父域 Cookie，未满足原方案的完整 Cookie 隔离要求。不能据此开放通用应用入口或宣称 M0 全部通过。

脱敏原始结果见 [结果 JSON](m0-access-results.json)，重复执行方式见 [工具说明](../tools/m0/README.md)。

## 环境与实验范围

- 实测微服：lzcos `1.6.2+fix.4`；CLI `2.0.9`；Linux 本机 Docker `29.9.2`，浏览器为本机 Chromium／Playwright。
- 在线校准 package、manifest、build、LPK 格式、secondary-domains、route 和 headers 七篇官方正文；均成功取得，来源与 SHA-256 见 [校准记录](deployment/m0-access-calibration.json)。未固定官方 commit，未把其他版本新增字段视为目标设备支持。
- 创建随机命名的独立临时 LPK，没有使用生产应用 ID；网关只监听临时应用容器的回环端口，使用 `exec` 路由，不开放 Docker socket。
- 本机通过 Docker CLI 独立启动一次性 Web 夹具容器，提供 Cookie 登录／WebSocket、静态页面和自签名 HTTPS 三个服务。容器只发布回环地址端口，原项目和 CoFleet 自有开发空间均未被部署或重建。
- 网关及本机连接器使用 `access-probe` feature，正常构建不启用。数据面复用现有 `agent_tunnel`／`serve_tunnel` 的有界反向 WSS 流；实验连接器读取已有节点配置，但使用新的实验设备 UUID，不向生产中枢注册。
- 只允许一个固定账号和三类固定服务；没有通用容器发现、任意地址输入、动态入口 API、持久化或多用户正式实现。

链路：浏览器 → 临时应用 HTTPS 域名 → 平台登录与身份 Header → 实验网关 → 独立 WSS 流 → 本机连接器 → Docker 已发布的回环端口。

## 已通过的检查

协议／服务端脚本 16 项检查通过，浏览器脚本 9 项兼容性检查通过；另外一个浏览器隔离门槛发现阻塞。完整结果保留为布尔值，不发布真实账号、节点标识、域名或凭据。

| 范围 | 实测结果 |
| --- | --- |
| Host 与域名 | 成功配置下 `exec` 路由保留实际 Host；登录服务、静态服务可使用不同来源 |
| 平台鉴权 | 无 Cookie、无效平台 Cookie、匿名伪造身份头被拒绝；已登录请求伪造身份不能替代平台真实身份 |
| 管理边界 | 应用来源访问管理路径返回 404；未知前缀被拒绝；跨来源访问管理接口被网关／浏览器阻断 |
| 请求头过滤 | 应用收不到平台 Cookie、CoFleet 控制 Cookie、身份票据或伪造转发链；应用 Authorization 可到达自己的服务 |
| 应用 API | 第三方应用自身的 `/api/session` 正常代理；仅隔离网关控制命名空间，不把所有 `/api/*` 都当作 CoFleet 管理接口拦截 |
| 应用登录 | 真实浏览器提交应用自身登录表单，收到 HttpOnly／Secure 应用 Cookie，再次访问保持应用登录 |
| 普通应用 Cookie | 支持多个 Set-Cookie；上游 Domain 被移除；保留为 host-only 的应用会话不发送给其他来源；上游试图设置保留平台 Cookie 名称被过滤 |
| WebSocket | 应用登录后可完成真实 WSS 握手与回显；没有平台登录及跨来源握手被拒绝 |
| 重定向 | 相对 Location 保留；批准的固定上游绝对来源映射到入口；外部登录地址保留；其他回环绝对重定向返回 502 |
| 错误与限制 | 未配置的应用路径返回 404，没有自动改写页面内容；自签名上游证书经默认信任库校验失败，返回 502，没有关闭验证 |
| 会话与离线 | 停止实验连接器后已有 WebSocket 关闭，新请求返回 503；仅移除一次性浏览器 context 中的平台 Cookie 后，新 HTTP 和 WebSocket 访问被拒绝 |

匿名 WebSocket 请求被平台重定向到登录页。aiohttp 会跟随该跳转，最终得到登录页 HTTP 200 并拒绝升级；脚本明确区分该情形和应用实际返回 101，不能把登录页的 200 当作 WebSocket 成功。

绝对重定向来源是实验夹具中明确批准的容器内部地址；它与动态发布的宿主端口分别处理。正式设计需要明确应用公开地址配置和批准的上游来源，不能把任何回环地址都重写成入口。

## 阻塞：不同来源仍可共享父域 Cookie 范围

补充浏览器实验：登录应用后，由应用页面脚本写入一个无害标记 Cookie，Domain 指向该微服的共同父域；随后查询管理来源的 Cookie，发现该标记存在。测试后立即移除标记，并销毁整个一次性 browser context。

示意：

```text
管理页面：control.box.example.test
应用页面：app.box.example.test
脚本可写：Domain=box.example.test; Path=/
结果：该 Cookie 也会发送到管理来源
```

这证明了“浏览器来源不同”和“Cookie 的允许 Domain 范围不同”不是同一件事。过滤代理响应的 Domain 属性只能约束 HTTP Set-Cookie，不能约束应用 JavaScript 调用 document.cookie。SameSite 也不能将同站点的兄弟子域变成独立 Cookie 安全边界。

本实验**没有尝试覆盖真实平台 Cookie，也没有证明可以读取 HttpOnly 凭据**；不能把结果扩大为账号凭据已被窃取。但它已经否定了原方案“第三方应用不能设置管理域 Cookie”的严格保证。响应头过滤、多个独立来源和管理 API 的 CORS 拒绝不能单独修复这一点。

因此，结果文件的 `strict_cookie_isolation_passed` 为 false，整体 `formal_access_gate` 为 blocked。保持生产入口关闭，不使用同源路径作为回退。

## 域名与部署兼容性发现

初始临时基础子域名含多个连字符：主域名可达，但其前缀域名在平台层返回“Unable to retrieve corresponding service information”，未到达实验网关；增加显式 upstream 前缀也未解决该组合。

重新安装临时包并改用不含连字符的随机基础子域名后，前缀访问成功，最终成功配置只需要 exec 路由。本次没有定位平台解析根因，**不据此宣称所有带连字符域名均不受支持**。后续只能沿用实测成功组合或进一步验证，不能直接从现有 `cofleet-test` 名称推导任意入口地址。

同包升级期间，实际分配域名没有随新 manifest 的期望值改变；网关必须以 LAZYCAT_APP_DOMAIN 校对真实分配结果。实验网关不一致时拒绝启动。上述验证均发生在临时包中，没有迁移或重新安装现有管理端。

第一次实验包还发现 content.tar 根目录继承了本地 0700 权限，导致容器 UID 1000 无法启动脚本；已修复为可遍历的包内目录与只读配置。包含密钥、私钥、原始 LPK 和运行记录的本机父目录仍保持私有，未提交仓库。

## 待补用例与后续决策

1. **真实跨账号**：用户确认暂时没有第二个测试账号，本轮先完成其余验证。已在本地受信入口边界测试其他用户被拒绝，但这不能替代第二真实账号的登录／域名／会话隔离实测。
2. **平台端会话撤销**：实测了无效 Cookie 和浏览器 Cookie 移除；没有执行现有用户的真实平台登出或服务端令牌撤销。不能承诺已建立流立即撤销，也不能把该用例标为完成。
3. **严格 Cookie 隔离方案**：0.7.0 的 M2 实现要求应用入口与管理入口属于不同 Cookie Site；未显式配置 `--access-domain`、入口域与管理域同站点或无法安全判定时，创建入口返回 412。代理同时过滤平台 Cookie、身份头和保留 Cookie 写入。该代码门禁没有替代真实微服域名、证书、平台登录、撤销和跨账号实测；默认 LPK 因而仍不启用应用入口。管理域与应用域分开也不自动隔离应用之间的父域 Cookie；各入口的授权 Cookie 及第三方应用自身的 Cookie 风险仍需单独验证。
4. 若平台未来提供真正独立的站点／Cookie 隔离机制，也可以先验证再采用。再增加一个兄弟子域不能解决当前发现；通用地禁用 JavaScript 或采用不允许 same-origin 的 sandbox 会破坏很多现有应用，不能作为无感兼容方案。
5. 若未来选择仅接入完全信任的自用应用，需要明确调整威胁模型和产品保证；本轮没有自动放宽该边界。

**后续顺序：M1/M2 的代码已经在 0.7.0 实现；正式启用仍取决于独立 Cookie Site 的微服路由、证书、真实项目、重启／断网和跨账号验收。** 在这些条件通过前保持默认入口关闭，不把代码完成或可达性通过等同于安全与多用户验收通过。


浏览器行为依据可对照 [RFC 6265 的 Domain 与存储模型](https://httpwg.org/specs/rfc6265.html#s-5.2.3) 和 [HTML 的 document.cookie 定义](https://html.spec.whatwg.org/multipage/dom.html#dom-document-cookie)。上述阻塞结论来自本次实际 Chromium 操作，不只是对规范的推测。
